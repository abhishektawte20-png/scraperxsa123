# Evidence checklist

Status of the DOM/visual evidence needed before each RTS workflow can be added to `registry/index.js` and enabled. A field moves from **Missing** to **Ready** only after all five evidence items exist for it:

1. The parent RTS section (screenshot or DOM extract).
2. The Add/Edit button that opens the control.
3. The opened form/popup.
4. Every dropdown, shown open, with its full option list.
5. The scoped Save button and the saved record afterward (to build read-back verification).

Evidence should be provided as raw outer HTML (copy from DevTools: right-click element → Copy → Copy outerHTML) plus a screenshot for visual context. Screenshots alone are not enough — they don't expose selectors.

## Status legend
- **Missing** — no evidence yet; field is not in the registry, or is present with `evidenceStatus: "missing"` and empty `candidates`.
- **In review** — evidence supplied, being turned into a registry entry.
- **Ready** — registry entry has real selector candidates and has been exercised at least once in a controlled test.

## Root cause found and fixed: bare domains in "source" fields

The enhanced error message above did its job: a screenshot of a real run showed five separate records failing validation — `businessEntity.nameVariations[1].source`, `company.industries[0].source`, `company.verticals[0].source`, `company.sicCodes[0].source`, and `company.sites[1].source` — four of them with the identical received value `"www.aromagrowstore.com"`, and one (`company.sites[1].source`) with garbled non-URL text (`"Aroma Grow Store opens in Niles - Illinois News Joint in-niles/"`).

The true pattern: the agent was consistently putting a bare domain in `source` fields, which previously required a strict, fully-qualified `https://` URL. Unlike the markdown-link corruption case (deliberately left unrepaired — proven to sometimes produce the wrong URL depending on where the corruption split), a bare domain has exactly one unambiguous, lossless interpretation: prepend `https://`. So this is now fixed at the validator level, not just asked for nicer in the prompt:

- `core/schema.js` adds `isBareDomainString`, `isValidSourceValue`, and `normalizeSourceValue`, unified into a single shared `SOURCE_FIELD` descriptor used everywhere a `source` field is checked (name variations, social media, research notes, industries, verticals, employee history, SIC codes, sites, management, and `businessEntity.websiteAddresses`), replacing ten separate copies of the same inline check so this can't drift or be missed on a future field.
- A bare domain in `source` (e.g. `"www.aromagrowstore.com"`) is now accepted and silently upgraded to `"https://www.aromagrowstore.com"` in the validated output — the panel and RTS never see the un-upgraded form.
- Genuinely invalid `source` text — anything that's neither a full URL nor a bare domain, like the garbled `company.sites[1]` case above — is still rejected with the same self-diagnosing error message (now naming "a bare domain" as an accepted form too, so the message stays accurate). That one is not safely auto-fixable (there's no reliable way to extract the intended URL from garbled prose), so it remains a manual, one-field correction via the redesigned per-field editor in the preview panel.
- The per-run prompt (`core/promptBuilder.js`) still asks Rovo for the stricter, ideal form (a full `https://` URL in every `source` field) — that's unchanged and still worth asking for — but the validator no longer depends on Rovo actually complying to avoid a hard failure.
- Tests added to `tests/test-static.mjs` covering: a bare domain in both a record-array `source` field and an envelope-shaped `source` field is accepted and normalized to `https://`, and garbled non-URL/non-domain text is still rejected.

## Full QA pass: a real, always-reproducible bug found by reading every file end to end

Prompted by feedback that the extension "is not able to work properly" with no specific error to go on, every core/registry/workflow/panel file was re-read in full (not just the files touched by recent fixes) to find bugs that hadn't surfaced as a specific user-reported error yet. This found one confirmed, always-reproducible correctness bug and three hardening gaps, all now fixed:

1. **Real bug, confirmed and fixed: `core/executionPlan.js` broke Email Default Structure on every publish.** For "envelope"-kind fields (a single value, not a repeatable list — e.g. `businessEntity.emailDefaultStructure`), the execution plan unwrapped the proposed change down to a bare scalar (`record.value`) before handing it to the preview/publish pipeline. But `applyEmailDefaultStructureValue()` (and every other workflow function) expects the *full* record object (`{value, action, source, confidence}`) so it can read `.action`/`.value` off it. Since a bare string has neither property, every real publish attempt for this field either threw `"'undefined' is not a supported Email Default Structure value"` (when RTS's dropdown was blank) or silently no-op'd while reporting nothing wrong (when it already had a value, which masked the bug in the common case). This is one of the 5 fields advertised as "live end to end" — it never actually worked when driven from the panel, even though the underlying workflow function itself was correctly unit-tested in isolation with a manually-constructed, correctly-shaped input. That's exactly why it went unnoticed: the integration point between the plan builder and the workflow was never exercised end to end until now. Fixed by always passing the full record through (`proposedValue: record`), and added both a unit test (`tests/test-static.mjs`, asserting the proposed value is an object with `.value`/`.action`, not a bare string) and a full live-DOM integration test (`tests/test-panel-smoke.mjs`) that drives the real panel → execution plan → workflow chain against a jsdom RTS fixture and confirms the dropdown is actually selected and saved.
2. **Correctness gap, fixed: multiple proposed Website Addresses could report false success.** RTS only has one Website Address field, and the workflow always writes the first selected entry — but if Rovo returned more than one candidate and the researcher selected more than one checkbox, every additional entry was silently given the *same* status as the first (including "savedValueVerified") without ever being written to the page. Fixed in `core/executionPlan.js`: only the first proposed Website Address is ever `pending`; every additional one is now marked `skipped` up front with an explicit reason, so it's never selectable and never falsely reported as applied.
3. **Hardening gap, fixed: a manual edit in the preview bypassed schema validation entirely.** The preview's helptext claimed an edit "is re-validated when you publish," but `content/panel.js` never actually re-ran the schema validator on an edited value before handing it to a workflow — a typo (e.g. blanking out a required field, or an invalid Name Type typed by hand before dropdowns existed) would only be caught deep inside a live DOM write, if at all. Fixed by wrapping every edited value back into its real jsonPath and re-running the actual `schema.validate()` before any workflow call; a validation failure now marks that one row "failed" with the same clear error text a bad paste would get, and the workflow is never called. This makes the existing helptext claim actually true.
4. **UX hardening, done: enum-shaped fields in the preview are now dropdowns, not free text.** `action`, `confidence`, Name Type, SIC Source, and Email Default Structure value are now rendered as `<select>` elements populated from the same schema enum / evidenced registry catalog used everywhere else, instead of a plain text input — eliminating an entire class of manual-edit typos (e.g. "Legal name" vs the exact catalog string "Legal Name") at the point where they're most likely to happen, rather than relying on the re-validation in (3) to catch them after the fact.

Verified end to end with a live (Playwright/Chromium) run against a jsdom-free, real-browser reconstruction of the evidenced RTS fixtures: pasting a full research JSON and publishing wrote and saved all 5 live fields correctly (name variation added, website address filled, **Email Default Structure dropdown correctly selected** confirming fix #1, research note appended, SIC code added with its source), with every Save button observed returning to disabled. All 88 automated tests pass (`node --test`).

## Two more real failures found from the very next real Rovo run

The user tried the fixed build against a real Rovo response for Aroma Grow Store and hit two new validation errors immediately — both fixed the same way as the `source` bare-domain issue: by finding the exact real value from the error message (no guessing) and asking whether there's exactly one safe, unambiguous repair.

The validator only accepted a full `https://` URL or a schemeless bare domain — a `http://` URL matched neither. Fixed by accepting `http://` wherever `https://` or a bare domain was already accepted (`websiteAddresses[].value` and every `source` field), and normalizing it up to `https://`, the same unambiguous-upgrade approach already used for bare-domain sources.

`core/promptBuilder.js` also gained two more worked "common mistakes" examples for these exact patterns (still asking Rovo for the ideal form, on top of the validator no longer needing it to comply). Re-validated the user's exact real JSON payload end to end after these fixes: it now parses with **zero errors and zero warnings**. New tests added to `tests/test-static.mjs` covering both cases. ## Identity lock: "insufficient" turned into a design decision, not a bug fix

Real report: publishing was blocked with "No shared strong identifier (pbId, entityId, or domain) was available to compare," even though the user confirmed the RTS profile they were on **did** show a PBID on screen.

Root cause, once traced through `core/identityLock.js`: Rovo has no way to ever discover an RTS-internal PBID or Entity ID from public web research, so `profileIdentity.pbId`/`.entityId` in its JSON output are always `null` in practice — they can never be the basis of a match. That leaves `domain` as the only field that can ever produce a strong comparison, read from `#domainValue` (falling back to `#webURL`). If that field happens to be blank on the RTS page — completely normal for a profile that has a PBID assigned but has never had its website filled in, i.e. exactly the kind of profile this tool exists to enrich — there is no value on either side left to compare, regardless of how correct everything else is. The visible PBID on the page was a red herring for this specific failure, since Rovo's JSON never claims a PBID to check it against.

This is a real design gap, not a wrong selector, and weakening the identity lock is a security-relevant decision — so it was put to the user directly (`AskUserQuestion`) rather than silently patched. Chosen fix, implemented in `content/panel.js`'s publish handler:

- `identityResult.status === "mismatch"` (an **active** conflict — e.g. domains disagree) is still an unconditional hard block. This can never be overridden; it's the strongest signal of a genuinely wrong profile.
- `identityResult.status === "insufficient"` (no conflict, but nothing strong to compare) no longer hard-blocks. Instead it shows a `window.confirm()` dialog with an explicit side-by-side comparison — the RTS page's PBID/formal name/domain vs. the researched company name/domain — and only proceeds if the researcher explicitly confirms. Declining cancels the publish with a clear message. This mirrors the human-in-the-loop principle already used everywhere else in this tool (preview before publish, confirm before any live write) rather than either silently bypassing the check or blocking a legitimate profile outright.

Two new tests in `tests/test-panel-smoke.mjs` cover both branches: declining the confirmation cancels with no fields applied, and accepting it proceeds and publishes normally. All 93 automated tests pass.

## Real-page testing round 2 (Champion Pool Supply, Peter Lucas Project Management): one confirmed bug fixed, one still open

**On the external review report someone shared:** it correctly identified the null-string bug above and the name-variations symptom (independently corroborating evidence, valuable), but its suggested code patches referenced a different codebase entirely (`content.js`, `writeNameVariation()`, `selectorRegistry.js` — none of which exist in this project) and included a fabricated CSS selector for a Keywords field (`#keywordsInput, input[placeholder*="keyword" i]`) that was never evidenced from the real page. None of that patch code was used. Its proposed fix for the name-variations bug (retry-clicking "Add" until the row count matches) was also not applied — if the root cause really is a persistent extra element outside any row structure, that retry loop would never converge, since the mismatch would remain no matter how many rows get added.

## Added: a real-browser end-to-end test (`tests/e2e/`)

Every bug found through this project's QA passes so far (the Email Default Structure publish bug, the identity-lock gap) was found by actually *running* the extension, not by reading the code — jsdom's simulation doesn't cover real event timing, focus/blur behavior, or rendering closely enough to have caught either on its own. `tests/e2e/live-browser.test.mjs` formalizes that into a permanent, repo-committed regression test: it drives the real, unmodified extension code in an actual Chromium browser (via Playwright) against a page assembled from the real evidenced fixtures (never a hand-maintained duplicate of the RTS DOM), then asserts on the real post-publish DOM state for all 5 live fields plus every Save button's disabled state. It's deliberately kept separate from `npm test` (`npm run test:e2e`, needs `npx playwright install chromium` once) so the fast jsdom suite stays dependency-light and can still run everywhere without a browser. See `tests/e2e/README.md`. Playwright itself is not usable *inside* a content script — it's an external Node-based browser driver, a fundamentally different thing from the extension's own in-page DOM code — so this is a testing tool, not a change to how the extension actually writes to RTS (which already uses the same native-setter-plus-event-dispatch technique Playwright itself uses internally).
